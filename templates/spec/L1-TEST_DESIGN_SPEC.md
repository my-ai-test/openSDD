# 测试设计规格

> 本文档定义从 AC（验收标准）系统化展开为完整测试用例的方法论。
> 一条 AC 不是 1:1 翻译为 1 个 test case，而是通过六层分层技术展开为 3~15 个 test cases。

---

## 1. 核心原则

```
AC  定义"系统应该做什么"（验收视角）
Test 验证"系统在各种情况下是否都能正确做到"（质量视角）

铁律：测试从 AC 推导，禁止从实现代码推导。
自检："如果实现方式变了但业务结果不变，测试还能过吗？"
  → 能过 = AC 驱动 ✓   |   不能过 = 代码驱动，需重写 ✗
```

---

## 2. 测试分层体系（DDD 增强版）

```
┌──────────────────────────────────────────────────────────────────┐
│ E2E 测试（Playwright）                                              │
│  覆盖完整用户旅程（UJ），跨 BC 端到端验证                              │
├──────────────────────────────────────────────────────────────────┤
│ 集成测试（真实 DB）                                                  │
│  验证 Repository / ORM 行为；事务回滚清理；跨层集成                    │
├──────────────────────────────────────────────────────────────────┤
│ 应用服务测试（Mock BC/Repository）                                   │
│  验证跨 BC 编排逻辑；Saga 补偿路径；幂等性                             │
├──────────────────────────────────────────────────────────────────┤
│ 聚合根单元测试（零 IO 依赖）⬅ DDD 核心                               │
│  纯 TypeScript，直接构造聚合根对象，验证不变量和领域事件                 │
├──────────────────────────────────────────────────────────────────┤
│ 六层 AC 展开（各层通用方法论）                                         │
│  L1 等价类 → L2 边界值 → L3 决策表 → L4 状态转换 → L5 组合 → L6 错误猜测│
└──────────────────────────────────────────────────────────────────┘
```

## 3. 聚合根单元测试规范（DDD 专属）

> 聚合根单元测试是 DDD 四层架构的核心测试，**零 IO 依赖**。

### 3.1 测试环境要求

| 要求 | 说明 |
|------|------|
| 无数据库 | 不得有任何 DB 连接或 Repository mock |
| 无 HTTP | 不得有任何外部 API 调用 |
| 无 Redis/Cache | 不得依赖缓存层 |
| 纯 TypeScript | 直接 `new AggregateRoot(...)` 构造，或用工厂方法 |

### 3.2 聚合根测试模板

```typescript
describe('{{AggregateRoot}}（聚合根单元测试）', () => {
  // 工厂函数：满足完整初始状态的聚合根
  function create{{AggregateRoot}}(overrides?: Partial<{{Props}}>) {
    return {{AggregateRoot}}.create({
      id: '{{test-uuid-001}}',
      // ...默认有效值
      ...overrides,
    });
  }

  describe('{{方法名}}', () => {
    // === AC-{NNN}: {AC 完整描述} ===

    // 不变量测试：验证业务规则被正确执行
    it('should throw DomainException when invariant violated', () => {
      const aggregate = create{{AggregateRoot}}({ status: '{{WrongStatus}}' });
      expect(() => aggregate.{{方法名}}()).toThrow(DomainException);
    });

    // 正常路径：验证状态变更
    it('should change status to {{NewStatus}} when {{条件}}', () => {
      const aggregate = create{{AggregateRoot}}({ status: '{{ValidStatus}}' });
      aggregate.{{方法名}}();
      expect(aggregate.status).toBe('{{NewStatus}}');
    });

    // 领域事件：验证事件被正确发出
    it('should emit {{EventName}} domain event', () => {
      const aggregate = create{{AggregateRoot}}({ status: '{{ValidStatus}}' });
      aggregate.{{方法名}}();
      const events = aggregate.pullDomainEvents();
      expect(events).toHaveLength(1);
      expect(events[0]).toBeInstanceOf({{EventName}});
    });
  });
});
```

### 3.3 聚合根测试检查项

- [ ] 每个聚合根有独立的 `*.aggregate.spec.ts` 测试文件
- [ ] 覆盖所有 `Invariant`（不变量）的正反向测试
- [ ] 覆盖所有合法/非法状态转换
- [ ] 覆盖领域事件是否被正确发出
- [ ] 工厂函数满足完整接口（无 `as any` 缺字段）
- [ ] CI 检测：`*.aggregate.spec.ts` 中无 DB/HTTP/Redis mock

## 4. 六层测试展开模型

```
┌────────────────────────────────────────────────────────────┐
│ L6: 错误猜测（Error Guessing）                              │
│  经验驱动：注入、并发、幂等、特殊字符、认证边界               │
├────────────────────────────────────────────────────────────┤
│ L5: 组合覆盖（Pairwise / Combinatorial）                   │
│  多参数交互：筛选组合、角色×操作×资源                        │
├────────────────────────────────────────────────────────────┤
│ L4: 状态转换（State Transition）                            │
│  生命周期：合法转换 + 非法转换 + 终态不可出                   │
├────────────────────────────────────────────────────────────┤
│ L3: 决策表（Decision Table）                                │
│  条件组合：权限矩阵、业务规则组合                            │
├────────────────────────────────────────────────────────────┤
│ L2: 边界值（Boundary Value Analysis）                       │
│  边界探测：min-1, min, max, max+1                           │
├────────────────────────────────────────────────────────────┤
│ L1: 等价类（Equivalence Partitioning）                      │
│  基础覆盖：有效值 + 无效值 + 空值                            │
└────────────────────────────────────────────────────────────┘
```

**基线要求**: L1 和 L6 对所有有输入/副作用的 AC 是强制的。

## 6. 每层详解

### L1 — 等价类划分

**方法**: 将每个输入参数的取值空间划分为有效等价类和无效等价类，每类取一个代表值。

**模板**:

| 参数 | 有效等价类 | 无效等价类 |
|------|-----------|-----------|
| `{参数名}` | {有效值描述} | null / undefined / 空字符串 |
| | | 格式错误 |
| | | 违反约束（超长、超范围） |

**测试标注**: `// AC-{NNN} L1: 等价类 — {具体描述}`

---

### L2 — 边界值分析

**方法**: 对每个有范围约束的参数，测试 `min-1, min, min+1, max-1, max, max+1`。

**模板**:

| 边界点 | 值 | 预期结果 |
|--------|-----|---------|
| min-1 | `{值}` | 拒绝 |
| min（恰好最小有效） | `{值}` | 通过 |
| max（恰好最大有效） | `{值}` | 通过 |
| max+1 | `{值}` | 拒绝 |

**测试标注**: `// AC-{NNN} L2: 边界值 — {参数名} min/max`

---

### L3 — 决策表

**方法**: 列出所有独立条件，穷举有意义的组合，为每列指定预期动作。

**模板**:

| 条件 | 场景1 | 场景2 | 场景3 |
|------|-------|-------|-------|
| {条件1} | T | T | F |
| {条件2} | T | F | T |
| **预期** | {结果} | {结果} | {结果} |

**测试标注**: `// AC-{NNN} L3: 决策表 — {条件描述}`

---

### L4 — 状态转换

**方法**: 绘制状态转换图，为每条合法转换写正向测试，为每个非法转换写反向测试。

**模板**:

```
合法转换（{N} 个正向 test）：
  {STATE_A} → {STATE_B}（{动作}）
  {STATE_B} → {STATE_C}（{动作}）

非法转换（{M} 个反向 test）：
  {STATE_A} → {STATE_C}（跳过中间状态）
  {TERMINAL} → 任何状态（终态不可出）
```

**测试标注**: `// AC-{NNN} L4: 状态转换 — {STATE_A} → {STATE_B}`

---

### L5 — 组合覆盖

**方法**: 使用 Pairwise 算法覆盖所有两两参数组合，避免全量组合爆炸。

**适用信号**: AC 有 3 个以上独立参数（如搜索接口的筛选条件）。

**测试标注**: `// AC-{NNN} L5: Pairwise — {参数组合描述}`

---

### L6 — 错误猜测

**通用检查清单**:

| 类别 | 检查项 |
|------|--------|
| 空值 | null, undefined, 空字符串, 空数组 |
| 注入 | SQL 注入（`'; DROP TABLE`）、XSS（`<script>`）、Prompt 注入 |
| 并发 | 两个请求同时操作相同资源 |
| 幂等性 | 重复提交同一操作 |
| 特殊字符 | Unicode emoji、中文、超长 UTF-8 |
| 认证边界 | 过期 Token、已吊销 Token、伪造签名 |
| 资源不存在 | 合法格式的 ID 但数据库中无记录 |
| 已删除资源 | 操作已软删除（IS_DELETED='Y'）的记录 |
| 网络异常 | 外部依赖超时、返回错误状态码 |
| 领域事件幂等 | 相同 eventId 被消费两次 |

**测试标注**: `// AC-{NNN} L6: 错误猜测 — {具体场景描述}`

## 7. 完整推导流程

```
Step 1: 关闭代码文件，打开 spec.md
Step 2: 读取目标 AC，分类（输入校验/CRUD/权限/状态/搜索/计算/集成/聚合根）
Step 3: 查 §5 映射表，确定必须/推荐使用哪些层
Step 4: 逐层展开 test cases（L1 → L6 顺序）
Step 5: 去重合并（L1 和 L6 可能产生重叠场景）
Step 6: 在每个 it 块标注 AC 编号 + 展开层
Step 7: 统计展开数（每条 AC ≥ 3 个 test cases）
Step 8: 运行测试 → 全部 FAIL（Red 状态）
Step 9: 编写实现代码让测试通过（Green 状态）
```

## 9. 质量门禁

| 门禁项 | 标准 |
|--------|------|
| 最低展开数 | 每条 AC ≥ 3 个 test cases |
| L1 强制 | 所有有输入的 AC 必须有 L1 等价类展开 |
| L6 强制 | 所有 AC 必须有 L6 错误猜测展开 |
| L3 权限强制 | 权限控制类 AC 必须有 L3 决策表展开 |
| L4 状态强制 | 状态流转类 AC 必须有 L4 状态转换展开 |
| 聚合根测试纯净 | `*.aggregate.spec.ts` 禁止出现 DB/HTTP/Redis mock |
| 无 TODO 占位 | 展开后不允许 `// TODO` 占位 |
| AC 全覆盖 | spec.md 中每条 AC 都有对应测试 |
| 断言质量 | 断言业务结果（状态值、返回数据），不断言内部实现细节 |
