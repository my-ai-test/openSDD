# /sdd-review-spec — 规格质量自检

> **工具 Skill**：对已有 spec 文件进行全面质量审查，
> 输出问题清单和改进建议，不自动修改文件。

---

## 输入

1. **待审查的 spec 文件路径**（可以是 feature spec、BC spec、或横截面 spec）
2. **审查类型**（可选：`ac`全面AC质量 / `completeness`完备性 / `quick`快速扫描）

---

## 执行流程

### Feature Spec（验收标准审查）

#### 检查 1：AC 格式合规性

逐条检查每个 AC：

```
✅ 合规：
  WHEN 用户提交有效申请
  THEN 系统创建状态为 PENDING 的 AccessRequest
  AND 返回 requestId

❌ 不合规（需修正）：
  - "系统应该正确处理" → 不可观测，改为具体结果
  - "验证输入格式" → 实现细节，改为"输入不符合格式时返回错误码 errorcode.xxx"
  - "性能良好" → 无具体数值，改为"响应时间 < 200ms（P95）"
```

#### 检查 2：六层覆盖完整性

对每个功能点，检查六层展开是否到位：

```markdown
| 功能点 | L1等价 | L2边界 | L3决策表 | L4状态转换 | L5组合 | L6错误猜测 |
|--------|--------|--------|---------|-----------|--------|-----------|
| 创建   | ✅ | ✅ | N/A | N/A | ❌缺少 | ✅ |
```

L1/L2/L6 是必须覆盖层（M），其他视 AC 类型决定。

#### 检查 3：端点覆盖矩阵

```
每个 API 端点是否至少有 1 条 AC？
→ 扫描 spec.md 中列出的端点
→ 与 AC 编号对应关系核对
→ 无对应 AC 的端点标记 ❌
```

#### 检查 4：错误码规范

```
正确格式：errorcode.{appname}.{module}.{exception}（4段）
常见问题：
  - 只写 "notFound" → 应为 "errorcode.{appname}.{module}.notFound"
  - 使用 HTTP 状态码代替错误码 → 业务异常统一 HTTP 200
```

#### 检查 5：BR（业务规则）完整性

```
检查 AC 中包含的数字约束是否已提取为独立 BR：
  - "不超过 200 个" → BR-001: 每用户最多 200 个未归档 Skill
  - "审批需 2 级" → BR-002: 申请需 {角色A} 初审 + {角色B} 终审
```

### BC Spec 审查

#### BC Spec 9 节完整性

```markdown
| 节 | 标题 | 状态 | 问题 |
|----|------|------|------|
| §1 | 职责声明 | ✅/❌ | |
| §2 | 统一语言 | ✅/❌ | |
| §3 | 聚合根清单 | ✅/❌ | |
| §4 | 值对象清单 | ✅/❌ | |
| §5 | 领域事件清单 | ✅/❌ | |
| §6 | 资源库 Port 接口 | ✅/❌ | |
| §7 | Context Map | ✅/❌ | |
| §8 | 业务规则 | ✅/❌ | |
| §9 | 不变量 | ✅/❌ | |
```

#### DDD 设计问题检查

```
❓ 聚合根是否过大？（属性超过 15 个 → 考虑拆分）
❓ 值对象是否有内在不变量？（无约束的 string 包装 → 可能是多余值对象）
❓ 领域事件是否命名规范？（过去式 + Event 后缀）
❓ BC 间是否存在直接引用（非 ID 引用）？
```

### 横截面 Spec 审查

#### DATA_SPEC 审查

检查 CLAUDE.md 规则 11（§11.1）中声明的企业 DB 规范是否满足。
若 CLAUDE.md 未配置企业规范，跳过此节（标注 N/A）。

常见检查项（以 CLAUDE.md §11.1 内容为准，以下为示例）：

```
☐ 表名格式符合 {prefix}_{name}_t 约定（查看 CLAUDE.md §11.1 确认前缀规则）
☐ 审计字段完整（CLAUDE.md §11.1 中声明的必填字段）
☐ 主键类型符合约定（UUID/自增等，以 CLAUDE.md §11.1 为准）
☐ 索引命名前缀符合约定
☐ 软删除字段存在（若项目使用软删除）
```

> **注**：具体规范内容从项目 CLAUDE.md §11.1 读取，本 Skill 不硬编码特定企业规范。

#### API_SPEC 审查

```
§9 端点契约完整性检查（每个端点必须有）：
  [ ] 方法 + 完整路径
  [ ] 权限要求
  [ ] 请求体 Schema（字段/类型/必填/约束）
  [ ] 成功响应 Schema（HTTP 状态码/字段/类型）
  [ ] 错误码列表（≥ notFound/forbidden/invalidInput 场景，业务异常返回 HTTP 200）
       → 权威来源：sdd-framework/standards/error-code-format.md

仅列在 §6 索引表中，§9 缺少详细契约 → 不合规
```

## 评分标准（可重复的扣分规则）

每个维度满分 100 分，按以下规则扣分：

| 维度 | 扣分规则 |
|------|---------|
| **AC 格式合规** | 每条不合规 AC（不可观测/含实现细节/无错误码）扣 10 分 |
| **六层覆盖完整** | L1/L2/L6 缺失（M 层）每处扣 15 分；L3/L4/L5 缺失（O 层）每处扣 5 分 |
| **端点覆盖矩阵** | 有 ❌ 端点（无对应 AC）每个扣 20 分，直至 0 分 |
| **BR 提取** | AC 中含数字约束未提取为独立 BR 每处扣 15 分 |
| **错误码规范** | 非完整 4 段格式每处扣 10 分；使用 HTTP 状态码替代错误码每处扣 20 分 |

> **严重度定义**：P1 = 扣 ≥15 分的问题（必须修复才能关闭任务）；P2 = 扣 <15 分的问题（建议改进）

## 输出格式

```markdown
## 规格审查报告 — {spec 文件名} @ {日期}

### 总体评分
| 维度 | 得分 | 扣分详情 |
|------|------|---------|
| AC 格式合规 | 80/100 | AC-003 不可观测(-10)，AC-007 无错误码(-10) |
| 六层覆盖完整 | 70/100 | 创建功能 L2 缺失(-15)，搜索功能 L4 缺失(-15) |
| 端点覆盖矩阵 | 100/100 | — |
| BR 提取 | 85/100 | 200字限制未提取为 BR(-15) |
| 错误码规范 | 90/100 | AC-002 使用短格式 notFound(-10) |

### 问题清单
| # | 位置 | 问题描述 | 严重度 | 建议 |
|---|------|---------|--------|------|
| 1 | AC-003 | 描述"系统正确处理"不可观测 | P1(-10) | 改为"系统返回 resourceId，状态为 DRAFT" |
| 2 | AC-007 | 缺少角色决策表 | P1(-15) | 补充 developer/reviewer/guest 三行矩阵 |
| 3 | BR节 | 200字限制未提取为独立 BR | P2(-15) | 新增 BR-003 |

### 必须修复（P1，共 N 项）
{每项：位置 + 具体改法}

### 建议改进（P2，共 M 项）
{每项：位置 + 具体改法}
```
